01 / Executive view

Why this MVP exists

Implemented core

BiteExpress turns restaurant records into an API that can create, retrieve, filter, and find nearby restaurants. The assessment describes a legacy monolith as the starting point; this repository implements a focused MongoDB-backed discovery MVP, not a migration of that system.

Business framing

Discovery problem

Users need useful restaurant results by location, cuisine, rating, and budget. Historic source data has inconsistent or missing values, so ingestion and search behavior must be explicit.

6–12 months · goal

Reliable local-to-team service

Keep ingestion repeatable, validate API inputs, measure search latency, and establish operational visibility before scaling traffic or adding more query types.

2–3 years · option

Modern discovery platform

Evaluate managed replication, security controls, regional placement, and richer search only when traffic, reliability targets, and product needs justify them.

02 / Architecture

Four views of the system

Select a view. Each diagram labels observed components separately from conceptual or proposed ones.

Assessment concept · not inspected

The repository contains no legacy code, schema, traffic profile, or deployment evidence. This diagram illustrates the assessment's monolith premise only.

Implemented · local Compose topology

Docker Compose runs one app container and one MongoDB container. A named volume persists MongoDB data; the local data/ directory is mounted read-only into the app.

Implemented · GET search path

Natural language is a deterministic parser, not an LLM. Explicit query parameters override supported inferred fields. Validated errors return ProblemDetail; missing-location records remain in ordinary searches and are excluded by $geoNear.

Proposed · no deployment claim

Replication, Atlas, dedicated search, and multi-region deployment are options for a later decision. They are not implemented or performance-tested in this repository.

03 / Data model

One restaurant, one document

The persisted model follows the restaurant read shape. Related values are embedded; cuisines remain an array; valid coordinates are GeoJSON.

Implemented
Illustrative shape · values abbreviated
{
  "_id": "UUID string",
  "name": "Restaurant name",
  "address": { "line1": "...", "city": "...",
               "locality": "...", "localityVerbose": "..." },
  "country": { "code": 1, "name": "India" },
  "location": { "type": "Point",
                "coordinates": [77.0639, 28.4674] },
  "cuisines": ["North Indian", "Mughlai"],
  "pricing": { "averageCostForTwo": 1500,
               "currency": "Indian Rupees(Rs.)", "priceRange": 3 },
  "rating": { "average": 3.8, "color": "Yellow",
              "text": "Good", "votes": 72 },
  "features": { "hasTableBooking": true,
                "hasOnlineDelivery": false,
                "isDeliveringNow": false,
                "switchToOrderMenu": false }
}

Embedding rationale

Address, country, price, rating, and operational features are read with their restaurant, so they live together. The small country-code mapping enriches imports and does not create a separate MongoDB collection.

IDs and missing values

API creation uses random UUID strings; CSV import derives deterministic UUID strings from source IDs for repeat imports. Optional fields can be null; unavailable or invalid coordinates produce no location.

GeoJSON & indexes

Coordinates are stored [longitude, latitude]. The observed indexes are MongoDB's default _id_ and location_2dsphere; the latter supports $geoNear. No other index is claimed.

04 / API surface

Four implemented endpoints

Spring MVC controllers expose HTTP DTOs; services map them to immutable restaurant records and query MongoDB.

Search contract

Pages are zero-based with size 1–100. Listing summaries expose address, city, country, cuisines, average rating, optional location, and distanceKm for nearby results. Distance sorting requires latitude and longitude. Cost filtering and sorting require currency.

Validation & errors

@Valid checks the POST body; search criteria validate filter ranges and combinations. Central @RestControllerAdvice returns ProblemDetail codes: VALIDATION_FAILED, INVALID_REQUEST, INVALID_FILTER, UNSUPPORTED_SEARCH, and RESTAURANT_NOT_FOUND.

06 / Design decisions

Why these choices fit

ChoiceReason in this MVPTrade-off or alternative
Embedded restaurant dataMost reads need address, country, pricing, rating, and features together.A normalized multi-collection model could reduce duplication but would add joins/lookups to common reads.
GeoJSON Point + 2dsphereIndexed $geoNear computes distances and nearby results in MongoDB.Missing coordinates cannot participate; deterministic sorting adds work after distance calculation.
Explicit importerBounded batches, deterministic IDs, and disabled-by-default startup make demos repeatable.Source anomalies remain visible; this is not a continuously synchronized ingestion pipeline.
Rule-based language parserSupported requests translate into the existing validated search criteria.Limited vocabulary; unsupported or dish-level requests return 400. LLM/vector search is absent.
Few indexesThe measured geo plan uses its index; the remaining 9,554-document scans are known.Case-insensitive regex and exact counts limit ordinary B-tree benefits. New indexes need representative A/B evidence.

MongoDB fits the MVP's document-shaped reads and geospatial search. This is an architectural rationale, not a claim that it outperforms every alternative.

07 / Reliability & scalability

A measured path forward

Proposals are contingent on usage, reliability targets, security needs, and deployment context. None of these capabilities is claimed as implemented.

Proposed
Next 6–12 months

Prove service reliability

  • Collect longer, representative p95/p99 and error-rate baselines with stable traffic and realistic data distribution.
  • Instrument slow queries and profile count, sort, and deep-page behavior; evaluate index or normalized-field changes in an isolated environment.
  • Define availability, backup, restore, and alerting requirements before choosing a production topology.
  • Review authentication, least-privilege database access, secrets, and import controls.
2–3 year options

Scale only with evidence

  • Evaluate Atlas or a managed replica set for availability and operations, with tested backup and restore procedures.
  • Consider dedicated search capabilities when product requirements exceed literal structured and rule-based queries.
  • Scale stateless API instances, then revisit pagination and data access based on measured traffic.
  • Plan regional placement, data residency, encryption, auditability, and disaster recovery around actual obligations.
08 / Evidence boundaries

What is known, and what is not

Implemented & tested

Four endpoints, CSV import, validation, structured and geospatial MongoDB queries, a bounded natural-language parser, Swagger, and Testcontainers-backed API tests. The load and explain scripts are repeatable.

Unmeasured or assumed

The legacy system is conceptual. Production traffic, availability, recovery time, cost, and business impact were not measured. The short local benchmarks do not prove scaling behavior or a before/after improvement.

Data boundary

The checkout includes data/zomato.csv for full imports, plus a three-row synthetic fixture and data/country-codes.csv for country names. Kaggle labels the dataset CC0: Public Domain. The source has pre-existing text anomalies; see encoding and repair notes.

Development provenance

AI assistance supported implementation, test drafting, review, and documentation. Behavior was checked with automated tests and MongoDB-backed verification; no AI model runs in the API.
